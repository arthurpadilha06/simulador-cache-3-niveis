# Three-Level Cache Memory Hierarchy Simulator

🇧🇷 [Leia em português](README.md)

Programming Assignment 2 for **BCC 266 – Computer Organization** at UFOP (Prof. Joubert Lima).

The project builds on the machine from Assignment 1 and adds **three cache memories (L1, L2 and L3)** between the CPU and the RAM. Every memory access from the CPU goes through an **MMU (Memory Management Unit, called *UCM* in the code)**. The MMU looks for the block in L1, then in L2, then in L3 and finally in RAM, and brings the block it finds up to cache 1. At the end of the run, the simulator shows how many hits and misses happened at each level and the total **hypothetical execution time**.

## How it works

| Feature | Implementation |
|---|---|
| Levels | Cache 1, Cache 2, Cache 3 and RAM |
| Block | 4 words |
| Mapping | Associative: the lookup first tries line `endBloco % tamanho` and then scans the whole cache |
| Write policy | Write-back: writes stay in cache 1 and only move down to the other levels when the block is evicted from it |
| Replacement | Uses a free line if there is one. If not, evicts a block with a high accumulated cost. If none qualifies, uses the "direct" line (`endBloco % tamanho`) |
| Program | 10,000 instructions generated by `instructionsGenerator.c` |

### Cost of each access

| Where the block was found | Cost |
|---|---|
| Cache 1 | 10 |
| Cache 2 | 110 |
| Cache 3 | 1,110 |
| RAM | 11,110 |

The hypothetical time is the sum of the costs of all accesses.

### Supported instructions

Each line of the instruction file has the format `opcode:b1:p1:b2:p2:b3:p3`, where `b` is the block address and `p` is the word inside the block (0 to 3).

| Opcode | Operation |
|---|---|
| 0 | Addition: `mem[b3][p3] = mem[b1][p1] + mem[b2][p2]` |
| 1 | Subtraction: `mem[b3][p3] = mem[b1][p1] - mem[b2][p2]` |
| 2 | Register → memory. If `b1` is even, uses register 1; if odd, register 2 |
| 3 | Memory → register. Same even/odd rule |
| -1 | End of program. The reader appends this instruction automatically |

## Building and running

The commands require `gcc` and start from the repository root.

**1. (Optional) Generate a new instruction file.** The generator writes to `tp2/instructions2.txt`, so it must be run from the root:

```bash
gcc instructionsGenerator.c -o gerador
```

```bash
./gerador
```

**2. Build and run the simulator.** `main` reads `instructions2.txt` from the current folder, so it must be run inside `tp2/`:

```bash
cd tp2
```

```bash
gcc -Wall *.c -o simulador
```

```bash
./simulador
```

### Sample output (16/32/64-block caches)

```
Memoria         Hit       Miss   Taxa hit
Cache 1       11360       3620     75.83%
Cache 2         205       3415      5.66%
Cache 3         262       3153      7.67%
RAM            3153

Tempo hipotetico de execucao: 35456800
```

The numbers change with every generated instruction file. (*Taxa hit* = hit rate; *Tempo hipotético de execução* = hypothetical execution time.)

### Changing the cache sizes

The sizes (in blocks) are set in `tp2/main.c`:

```c
iniciarCPU(&cpu, &ram, 16, 32, 64);   // cache 1, cache 2, cache 3
```

### Generator parameters

The parameters are `#define`s at the top of `instructionsGenerator.c`:

| Parameter | Default | Meaning |
|---|---|---|
| `N_INST` | 10000 | number of instructions |
| `N_FOR` | 5 | size of the repeated instruction group |
| `N_MEM` | 1000 | number of memory blocks used |
| `N_PROB` | 50 | probability (%) of repeating the group |

## Results

Average of 5 runs with 50% instruction repetition:

| Machine (cache 1/2/3) | Cache 1 hits | Cache 2 hits | Cache 3 hits | RAM accesses | Hypothetical time |
|---|---|---|---|---|---|
| M1 (4/8/16) | 2,291 | 12,261 | 1,203 | 5,238 | 60.9 M |
| M2 (16/32/64) | 17,038 | 312 | 325 | 3,319 | 37.4 M |
| M3 (64/128/256) | 17,290 | 656 | 970 | 2,077 | 24.4 M |
| M4 (256/512/1024) | 18,245 | 1,541 | 247 | 960 | 11.3 M |

What the tests showed:

- Time drops sharply once the cache starts to grow and almost stops dropping after 16 blocks. From that size on, the repeated instruction group fits in the cache.
- 16 blocks already deliver **84% of the total gain**. Going up to 512 blocks makes the cache 32 times more expensive to gain the remaining 16%.
- A larger repeated group (`N_FOR`) needs more cache to fit. When the program uses a lot of memory (`N_MEM`), increasing the cache helps little.

**Conclusion:** the cache does not need to be large; it only needs to fit what the program is using at the moment. The full analysis, with charts, is in the [report](relatorio_caches.pdf) (in Portuguese).
